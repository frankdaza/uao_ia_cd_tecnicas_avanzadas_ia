\begin{abstract}
% ============================================================
Este artículo presenta el diseño e implementación de un sistema de
preguntas y respuestas (\textit{Q\&A}) basado en información obtenida
mediante \textit{web scraping} aplicado al dominio institucional de la
Fundación Valle del Lili. En su fase 2, el sistema se organiza en siete
módulos secuenciales: (1)~extracción automatizada mediante un
\textit{crawler} de búsqueda en anchura (BFS) que respeta las directivas de
\code{robots.txt}, con un corpus de 1\,000 páginas HTML descargadas en
aproximadamente 51 minutos; (2)~conversión a Markdown con \textit{front
matter} YAML, produciendo 1\,000 documentos en
\code{data/markdown/valledellili-org/}; (3)~recuperación léxica con el
algoritmo BM25 Okapi, que selecciona y concatena los tres documentos de
mayor puntuación como contexto enriquecido; (4)~composición del
\textit{prompt} con instrucciones anti-alucinación; (5)~generación de
respuestas con ocho modelos de lenguaje disponibles bajo una interfaz
uniforme —tres modelos locales en Ollama (\code{llama3.1:8b},
\code{gemma4:e2b} y \code{gemma4:e4b}) y cinco modelos en la nube por la API
de OpenAI (\code{gpt-4o}, \code{gpt-4o-mini}, \code{gpt-4-turbo},
\code{chatgpt-4o-latest} y \code{gpt-3.5-turbo})—; (6)~un backend HTTP
construido con FastAPI, Uvicorn y \code{sse-starlette} que expone el
\textit{pipeline} como servicio REST con transmisión \textit{Server-Sent
Events} (SSE) y un modo dual que consulta Ollama y OpenAI con una sola pasada
BM25; y (7)~un \textit{frontend} \textit{single page application} (SPA)
desarrollado en React 19 + Vite 7 + TypeScript, con Tailwind CSS v4 y
\textit{shadcn/ui}, que renderiza la respuesta en tiempo real y permite
editar el \textit{prompt} de sistema sin modificar el código fuente. Se
diseñó un protocolo de evaluación reproducible con 23 preguntas de
referencia distribuidas en cinco categorías temáticas, con métricas de
precisión de recuperación, Recall@3, tasa de abstención y latencia media
por modelo.
\end{abstract}

\section{Introducción}
% ============================================================

La creciente disponibilidad de modelos de lenguaje de gran escala
(\textit{Large Language Models}, LLM) ha abierto nuevas posibilidades para
la construcción de sistemas de preguntas y respuestas capaces de interactuar
en lenguaje natural sobre dominios específicos. Sin embargo, el uso de LLM
sin restricción sobre el dominio de conocimiento conlleva el fenómeno de
alucinación: la generación de información plausible pero factualmente
incorrecta \cite{lewis2020rag}.

La Fundación Valle del Lili es una institución hospitalaria de referencia en
Colombia que dispone de un sitio web institucional con información sobre
servicios médicos, trámites administrativos, especialidades y datos de
contacto. Un sistema automatizado de Q\&A sobre esta información reduciría
la carga en canales de atención al cliente y mejoraría la accesibilidad para
pacientes y público en general.

Este trabajo propone un \textit{pipeline} RAG completo que aborda el
problema en fases secuenciales bien delimitadas: adquisición de datos,
procesamiento documental, recuperación de contexto relevante, generación
de respuestas, exposición del \textit{pipeline} como servicio HTTP y
consumo desde una interfaz web moderna. La recuperación se implementa
mediante el algoritmo BM25 Okapi \cite{robertson2009bm25}, que selecciona
los tres archivos más relevantes ante cada consulta y los concatena como
contexto único. Estos documentos se presentan al LLM junto con un
\textit{prompt} de sistema que restringe la respuesta al dominio del corpus.

La contribución principal de este trabajo consiste en demostrar que es
posible construir un sistema RAG funcional, trazable y libre de alucinaciones
sin recurrir a bases de datos vectoriales ni a modelos de \textit{embedding},
lo que simplifica el despliegue y reduce los requisitos computacionales en
la fase inicial del proyecto. Como contribución adicional de la fase 2, el
sistema se desacopla en un \textit{backend} HTTP con FastAPI + SSE y un
\textit{frontend} SPA construido con React 19 + Vite 7 + Tailwind CSS v4 +
\textit{shadcn/ui}, lo que habilita interfaces de alto impacto visual,
modo dual de comparación entre modelos locales y en la nube, y reutilización
del API por scripts de evaluación y por los módulos posteriores del curso.

El artículo se organiza de la siguiente manera: la Sección~\ref{sec:arq}
describe la arquitectura general; las Secciones~\ref{sec:scraping}
a~\ref{sec:api_ui} detallan cada módulo; la Sección~\ref{sec:eval} presenta
el protocolo de evaluación y los resultados; finalmente, las
Secciones~\ref{sec:disc} y~\ref{sec:conc} ofrecen la discusión y las
conclusiones.

\subsection{Respeto a \texttt{robots.txt} e Idempotencia}

Antes de visitar cualquier URL, el sistema consulta la clase
\code{GestorRobots}, que carga y analiza el archivo \code{robots.txt} del
dominio con carga perezosa (\textit{lazy loading}). Si la directiva prohíbe
el acceso o la lectura falla, el gestor adopta un modo conservador que
rechaza todas las rutas. El \textit{Crawl-Delay} declarado en
\code{robots.txt} se respeta si supera el \code{delay\_segundos} configurado.

Para garantizar idempotencia, cada página descargada se persiste junto a un
archivo \textit{sidecar} JSON que almacena su hash SHA-256. En ejecuciones
posteriores, si el contenido no ha cambiado, la página se omite sin realizar
una nueva petición HTTP.

Ante errores transitorios (códigos 5xx o 429), el sistema aplica retroceso
exponencial con esperas de 1, 2 y 4 segundos entre intentos sucesivos.

\subsection{Salida del Módulo}

Por cada página exitosa, el \textit{crawler} genera en
\code{data/raw/valledellili-org/} un par de archivos:

\begin{itemize}
    \item \textbf{HTML}: contenido bruto de la respuesta HTTP.
    \item \textbf{JSON sidecar}: URL canónica, código de estado, hash SHA-256,
          profundidad de rastreo y marca de tiempo.
\end{itemize}

Las descargas se registran de forma acumulativa en
\code{data/raw/\_log.jsonl}, lo que permite auditar qué URLs se visitaron,
cuáles se omitieron por \code{robots.txt} o por hash idéntico, y cuáles
fallaron en red.

\section{Módulo de Procesamiento Documental}
\label{sec:conversion}
% ============================================================

\subsection{Limpieza del HTML}

Antes de la conversión, se elimina el ruido léxico mediante BeautifulSoup4:
se suprimen los elementos \code{<script>}, \code{<style>}, \code{<nav>},
\code{<header>}, \code{<footer>}, \code{<iframe>} y los banners de cookies.
Esta etapa mejora directamente la calidad de la recuperación BM25 al reducir
términos irrelevantes en el vocabulario del corpus.

\subsection{Conversión a Markdown}

La conversión HTML $\rightarrow$ Markdown se realiza con la biblioteca
\code{markdownify}~\cite{markdownify}, configurada con encabezados ATX
(\code{\#}) y viñetas con guion. El resultado se normaliza para eliminar
saltos de línea consecutivos excesivos (máximo dos seguidos).

\subsection{Front Matter YAML}

Cada archivo Markdown incorpora un bloque de metadatos YAML al inicio:

\begin{lstlisting}[language=yaml, caption={Ejemplo de front matter generado
automáticamente}, label={lst:fm}]
---
source_url: https://valledellili.org/atencion-al-paciente/
titulo: "Atención al Paciente"
seccion: atencion-al-paciente
fecha_extraccion: '2026-04-27'
idioma: es
hash: a3f2c1d9...
---
\end{lstlisting}

El campo \code{source\_url} es fundamental para la trazabilidad: se expone
al usuario junto a cada respuesta generada. El campo \code{hash} permite la
idempotencia de re-exportaciones.

\subsection{Salida del Módulo}

Los archivos Markdown se almacenan en
\code{data/markdown/valledellili-org/}. El script \code{export\_markdown.py}
es idempotente: omite la re-conversión si el hash del HTML coincide con el
registrado en el Markdown existente, a menos que se invoque con la bandera
\code{--forzar}.

\section{Módulo de Recuperación BM25}
\label{sec:bm25}
% ============================================================

\subsection{Algoritmo BM25 Okapi}

La recuperación de información se basa en el algoritmo BM25
Okapi~\cite{robertson2009bm25}, una función de puntuación probabilística que
pondera la frecuencia de los términos de la consulta en cada documento y
normaliza por la longitud del documento. La puntuación de un documento $D$
ante una consulta $Q = \{q_1, q_2, \ldots, q_n\}$ se define como:

\begin{equation}
\mathrm{BM25}(D,Q)
= \sum_{i=1}^{n} \mathrm{IDF}(q_i)
  \cdot \frac{f(q_i,D)\,(k_1+1)}
             {f(q_i,D) + k_1\!\left(1 - b + b\,\dfrac{|D|}{\overline{dl}}\right)}
\label{eq:bm25}
\end{equation}

donde:
\begin{itemize}
    \item $f(q_i, D)$: frecuencia del término $q_i$ en el documento $D$.
    \item $|D|$: longitud del documento en número de tokens.
    \item $\overline{dl}$: longitud media de los documentos del corpus.
    \item $k_1 = 1.5$: parámetro de saturación de frecuencia de término.
    \item $b = 0.75$: parámetro de normalización de longitud.
    \item $\mathrm{IDF}(q_i)$: frecuencia inversa de documento:
\end{itemize}

\begin{equation}
\mathrm{IDF}(q_i)
= \log \frac{N - \mathrm{df}(q_i) + 0.5}{\mathrm{df}(q_i) + 0.5}
\label{eq:idf}
\end{equation}

siendo $N$ el total de documentos del corpus y $\mathrm{df}(q_i)$ el número
de documentos que contienen el término $q_i$.

\subsection{Tokenización}

Antes de indexar el corpus y de procesar cada consulta, los textos se
someten al siguiente proceso:

\begin{enumerate}
    \item \textbf{Normalización Unicode}: descomposición NFD y eliminación de
          marcas combinantes (tildes, diéresis), de modo que, por ejemplo,
          \textit{médico} se tokeniza igual que \textit{medico}.
    \item \textbf{Minúsculas}: conversión completa a minúsculas.
    \item \textbf{Extracción de tokens}: expresión regular \code{\textbackslash w+}
          sobre texto Unicode.
    \item \textbf{Filtrado}: se descartan tokens de longitud $< 2$ y los
          pertenecientes a la lista de \textit{stopwords} del español
          (\textit{de, la, el, en, y, que, los, las, del, un, una, por, con,
          para, se, su, es, al, lo, a, o}, entre otras).
\end{enumerate}

\subsection{Selección de Top-3 Documentos}

A diferencia de los enfoques que recuperan un único documento, este sistema
selecciona los \textbf{tres documentos con mayor puntuación BM25}. Formalmente,
dado el conjunto de puntuaciones $\{s_1, s_2, \ldots, s_M\}$ calculadas para
los $M$ documentos del corpus, se selecciona el subconjunto:

\begin{equation}
\mathcal{C}
= \underset{|\mathcal{C}|=3,\; D \in \mathcal{D}}{\arg\max}\;
  \mathrm{BM25}(D, Q),
\quad s_j > 0
\label{eq:top3}
\end{equation}

Los documentos en $\mathcal{C}$ se ordenan de mayor a menor puntuación y se
concatenan para conformar el contexto que se envía al LLM. Esta estrategia
reduce el riesgo de que un único documento no contenga toda la información
necesaria para responder preguntas que abarcan varias secciones del sitio.

\subsection{Implementación}

El módulo \code{src/retrieval/recuperador.py} implementa la clase
\code{RecuperadorBm25} usando la biblioteca \code{rank-bm25}~\cite{rankbm25}.
El índice se construye en memoria al inicializar la clase, cargando todos los
archivos \code{*.md} del directorio \code{data/markdown/valledellili-org/}.
Sobre el corpus actual de 1\,000 documentos Markdown, la indexación
completa se realiza en el arranque del servidor FastAPI en unos pocos
segundos, lo que permite reindexar bajo demanda a través del endpoint
\code{POST /api/recargar-corpus} sin reiniciar el servicio. El método
\code{buscar(pregunta)} retorna una lista de objetos
\code{DocumentoRecuperado} con los atributos: \code{ruta}, \code{titulo},
\code{source\_url}, \code{contenido} y \code{score}.

\subsection{Prompt de Sistema Anti-Alucinación}

El \textit{prompt} de sistema predeterminado instruye al LLM para que actúe
como \textit{"Lili"}, asistente virtual de la Fundación Valle del Lili. Las
directivas fundamentales son:

\begin{itemize}
    \item Responder \textbf{únicamente} con información presente en el
          contexto entregado.
    \item Emitir la frase \textit{"No tengo información suficiente"} si la
          consulta no puede responderse con el contexto disponible.
    \item No inventar números de teléfono, correos electrónicos, direcciones
          ni especialidades médicas.
    \item Mantener un tono profesional y cálido en español colombiano.
    \item Limitar la respuesta a seis oraciones (salvo listas o pasos) y
          estructurarla en Markdown.
\end{itemize}

Estas restricciones constituyen la estrategia primaria de mitigación de
alucinaciones, complementada por la restricción de dominio que impone el RAG.

válidos para el parámetro \code{model} de \code{chat.completions}:
\code{gpt-4o}~\cite{openai2024gpt4o}, \code{gpt-4o-mini},
\code{gpt-4-turbo}, \code{chatgpt-4o-latest} y \code{gpt-3.5-turbo}. La
selección se hace en tiempo de ejecución desde el \textit{frontend} sin
modificar el código. La clave de autenticación se configura con la variable
de entorno \code{OPENAI\_API\_KEY} en el archivo \code{.env}, leída con
\code{pydantic-settings}. El acceso se realiza mediante la API oficial de
OpenAI~\cite{openai2024api}.

Ante errores HTTP 429 (\code{RateLimitError}), el cliente aplica hasta tres
reintentos con \textit{backoff} que respeta el encabezado \code{Retry-After}
si la respuesta lo expone; en ausencia de dicho encabezado, usa una espera
exponencial acotada. Otros errores de autorización o facturación
(\code{AuthenticationError}, \code{PermissionDeniedError}) se traducen a
mensajes explícitos en español que el frontend renderiza en un
\textit{toast} de error. El cliente implementa la misma interfaz que
\code{ClienteOllama}, lo que permite al \code{PipelineQa} orquestar ambos
\textit{backends} de forma uniforme, incluyendo el modo dual descrito en
la Sección~\ref{sec:api_ui}.

\section{Backend HTTP FastAPI + SSE y Frontend React 19}
\label{sec:api_ui}
% ============================================================

En la fase 2 del proyecto, la interfaz monolítica Gradio del MVP se
reemplazó por una arquitectura cliente-servidor de dos capas: un
\textit{backend} HTTP en \code{src/api/} que expone el \code{PipelineQa}
como servicio REST con \textit{streaming} SSE, y un \textit{frontend}
\textit{single page application} desarrollado en \code{frontend/}. Esta
separación, discutida con mayor detalle en~\cite{decision_fvl_fase2}, permite
reutilizar el API desde \textit{scripts} de evaluación, cuadernos de
experimentación y futuros módulos del curso sin acoplarse a la capa de
presentación.

\subsection{Backend HTTP FastAPI}

El \textit{backend} se construye con FastAPI~\cite{fastapi},
Uvicorn~\cite{uvicorn} como servidor ASGI y
\code{sse-starlette}~\cite{ssestarlette} para los endpoints de
\textit{streaming}. La configuración se carga desde \code{.env} con
\code{pydantic-settings}, incluyendo las variables \code{ALLOWED\_ORIGINS}
(dominios permitidos en \code{CORSMiddleware}) y \code{OPENAI\_API\_KEY}.

Al arrancar la aplicación, un \textit{context manager} de ciclo de vida
instancia una única vez el \code{PipelineQa}, lo que evita reconstruir el
índice BM25 en cada petición. Las dependencias HTTP acceden al pipeline
mediante \code{Depends(obtener\_pipeline)}. Los mensajes de error se
traducen a códigos HTTP estándar con cuerpos JSON tipados por modelos
Pydantic v2. La Tabla~\ref{tab:endpoints} resume los endpoints disponibles.

\subsection{Streaming SSE Token a Token}

Los endpoints de \textit{streaming} devuelven una secuencia de eventos
\textit{Server-Sent Events} con el campo \code{data} serializado en JSON.
Cada evento declara un campo \code{tipo} (\code{token}, \code{final},
\code{fuentes} o \code{error}) y, en los casos aplicables, un campo
\code{motor} que identifica si proviene de Ollama o de OpenAI. El servidor
emite además comentarios SSE \code{: keepalive} cada quince segundos para
mantener viva la conexión a través de \textit{proxies} intermediarios.

\begin{lstlisting}[caption={Ejemplo simplificado de flujo SSE emitido
por \code{POST /api/qa/stream}}, label={lst:sse_flow}]
data: {"tipo": "token", "motor": "ollama", "texto": "La "}
data: {"tipo": "token", "motor": "ollama", "texto": "Fundacion "}
...
data: {"tipo": "final", "motor": "ollama",
       "texto": "...", "latencia_ms": 1823}
data: {"tipo": "fuentes", "fuentes": [...]}
: keepalive
\end{lstlisting}

En el navegador, el objeto \code{EventSource} nativo no permite enviar
peticiones \code{POST} con cuerpo JSON; por esta razón, el \textit{frontend}
implementa un cliente propio basado en \code{fetch} combinado con
\code{ReadableStream} y \code{TextDecoderStream}. Este patrón mantiene la
semántica SSE y a la vez soporta cuerpos de petición arbitrarios.

\subsection{Modo Dual Ollama + OpenAI}

El modo dual, gatillado cuando el usuario activa simultáneamente ambos
\textit{backends}, se resuelve con una única invocación a
\code{preparar\_contexto\_inferencia(pregunta, prompt)} que construye los
mensajes una sola vez a partir del top-3 BM25. El endpoint
\code{POST /api/qa/dual/stream} reutiliza ese contexto y emite primero
todos los eventos con \code{motor:"ollama"} y, a continuación, todos los
eventos con \code{motor:"openai"}. Esto evita duplicar el costo de la
recuperación BM25 y entrega al usuario dos respuestas independientes que
comparten exactamente las mismas fuentes. El \textit{frontend} renderiza
ambas en el componente \code{DualResponseView}, con dos columnas
independientes y una zona de fuentes compartida.

El \textit{frontend} vive en la carpeta \code{frontend/} y se compone de

El sistema de diseño adopta tokens CSS alineados a la identidad
institucional de la Fundación Valle del Lili: morado primario

La SPA conserva las dos funcionalidades diferenciales heredadas del MVP:

\begin{itemize}
    \item \textbf{Prompt de sistema editable}: el componente
          \code{SystemPromptEditor} permite modificar en caliente las

\code{\{"tipo":"error"\}} que se traduce en un \textit{toast} explicativo
con la causa probable y la acción sugerida.

\section{Discusión}
\label{sec:disc}
% ============================================================

\subsection{Ventajas del Enfoque BM25 sin Embeddings}

La decisión de emplear BM25 en lugar de \textit{embeddings} densos y bases de
datos vectoriales responde a criterios de simplicidad, trazabilidad y
eficiencia. BM25 no requiere un modelo de \textit{embedding} preentrenado, no
demanda GPU para la indexación y produce puntuaciones directamente
interpretables en términos de frecuencia de términos. Sobre el corpus
actual de 1\,000 documentos Markdown el índice se reconstruye en unos pocos
segundos al arranque del \textit{backend}, y cada búsqueda se resuelve en
tiempo $O(n \cdot |Q|)$ donde $n$ es el número de documentos.

Además, el sistema de recuperación con top-3 documentos amplía la cobertura
contextual respecto a la recuperación de documento único, permitiendo que el
LLM sintetice información distribuida en varias páginas del sitio web.

\subsection{Ventajas de la Separación Backend / Frontend}

La arquitectura FastAPI + SSE desacoplada del consumidor web introduce
ventajas prácticas frente al monolito Gradio del MVP. El mismo API HTTP
puede ser invocado por el \textit{frontend} React, por los \textit{scripts}
de evaluación (\code{scripts/evaluar\_qa.py}) o por futuros clientes
—incluidos los experimentos del módulo 2 sobre \textit{chunking} semántico
y recuperación densa— sin duplicar la lógica de orquestación del
\code{PipelineQa}. El \textit{frontend}, al consumir un contrato JSON/SSE
estable, evoluciona con ciclos de iteración propios (diseño,
accesibilidad, branding) sin bloquearse en la capa Python. Finalmente, la
interfaz uniforme de los clientes de Ollama y OpenAI facilita el modo
dual: el costo de recuperación BM25 se paga una sola vez y el mismo
contexto alimenta ambos motores en paralelo, lo que habilita comparativas
directas entre modelos locales y en la nube.

\subsection{Limitaciones Identificadas}

\begin{enumerate}
    \item \textbf{Truncamiento de contexto}: si la concatenación de los tres
          documentos supera los 8\,192 tokens del parámetro \code{num\_ctx}
          por defecto, Ollama trunca el contexto de forma silenciosa, lo
          que puede degradar la calidad de la respuesta. El corpus ampliado
          a 1\,000 documentos incrementa la probabilidad de que los
          archivos recuperados sean largos y exijan elevar
          \code{OLLAMA\_NUM\_CTX} o considerar \textit{chunking}.
    \item \textbf{Ambigüedad léxica}: BM25 no captura similitud semántica;
          términos sinónimos o expresiones parafrasadas pueden no coincidir
          léxicamente con el vocabulario del corpus, produciendo recuperaciones
          incorrectas.
    \item \textbf{Dependencia del servicio Ollama}: los modelos locales
          requieren que el proceso Ollama esté en ejecución y que los modelos
          hayan sido descargados previamente.
    \item \textbf{Costo de la API}: el uso de los modelos OpenAI
          —especialmente \code{gpt-4o} y \code{gpt-4-turbo}— genera consumo
          de tokens facturables; el cliente
          \code{src/qa/cliente\_openai.py} implementa manejo de
          \code{RateLimitError} con \textit{backoff}, pero el equipo debe
          vigilar los límites de cuota del plan contratado.
    \item \textbf{Doble \textit{runtime} de desarrollo}: la separación
          \textit{backend} Python (\code{uv}) y \textit{frontend} Node
          (\code{pnpm}) requiere instalar ambos entornos para desarrollar,
          lo que incrementa el costo de \textit{onboarding} respecto al
          monolito Gradio.
\end{enumerate}

\subsection{Trabajo Futuro}

Para la siguiente fase del proyecto se contempla migrar a una arquitectura
basada en \textit{chunking} semántico, modelos de \textit{embedding} y una
base de datos vectorial (Chroma o FAISS), lo que permitirá superar las
limitaciones léxicas de BM25 y manejar documentos de mayor longitud sin
riesgo de truncamiento.

\section{Conclusiones}
\label{sec:conc}
% ============================================================

Este trabajo presentó un sistema RAG completo para la Fundación Valle del
Lili, construido con herramientas de código abierto y ejecutable en hardware
de consumo sin necesidad de GPU. Los aportes principales son:

\begin{enumerate}
    \item Un \textit{pipeline} de adquisición y procesamiento documental
          robusto que respeta \code{robots.txt} y garantiza idempotencia
          mediante hashes SHA-256, con un corpus escalado en la fase 2 a
          1\,000 páginas HTML y 1\,000 documentos Markdown con
          \textit{front matter} YAML.
    \item Un mecanismo de recuperación BM25 que selecciona y concatena los
          tres documentos más relevantes, ampliando la cobertura contextual
          respecto a la recuperación de documento único.
    \item La integración de ocho modelos de lenguaje heterogéneos —tres
          locales con Ollama (\code{llama3.1:8b}, \code{gemma4:e2b},
          \code{gemma4:e4b}) y cinco en la nube con la API de OpenAI
          (\code{gpt-4o}, \code{gpt-4o-mini}, \code{gpt-4-turbo},
          \code{chatgpt-4o-latest} y \code{gpt-3.5-turbo})— bajo una
          interfaz uniforme que permite comparación directa sin modificar
          el código.
    \item Una separación clara en dos capas: un \textit{backend} HTTP
          FastAPI + \code{sse-starlette} que expone el \code{PipelineQa}
          como servicio REST con \textit{streaming} SSE token a token y
          con modo dual Ollama + OpenAI sobre una sola pasada BM25.
    \item Un \textit{frontend} \textit{single page application} construido
          con React 19 + Vite 7 + TypeScript + Tailwind CSS v4 +
          \textit{shadcn/ui}, que encapsula una experiencia de usuario de
          alto impacto visual con identidad institucional, modo claro y
          oscuro, \textit{prompt} de sistema editable en caliente y panel
          de trazabilidad BM25.
    \item Un protocolo de evaluación reproducible con 23 preguntas de
          referencia y cuatro métricas de calidad de recuperación y
          generación, ejecutable contra cualquier subconjunto de los ocho
          modelos integrados.
\end{enumerate}

Los resultados de la evaluación (Tabla~\ref{tab:resultados}) permitirán
comparar objetivamente el comportamiento de los ocho modelos y confirmar la
hipótesis de que BM25 constituye una base sólida para un sistema RAG de
primera fase antes de incorporar técnicas de recuperación densa. La
separación \textit{backend}/\textit{frontend} introducida en la fase 2
deja lista la infraestructura para reutilizar el API desde los experimentos
del módulo 2 sobre \textit{chunking} semántico, \textit{embeddings} y
bases de datos vectoriales.
